# 用户级 Cyber 历史超限拦截策略

## Purpose

允许管理员对特定用户关闭 Cyber 会话检查中因历史候选超限而直接拒绝的策略，保持其他安全行为与有界查询。

## Requirements

### Requirement: 管理员用户编辑开关

管理员用户编辑弹窗必须提供可见标签“Cyber 历史超限拦截”及中英文说明，复用现有控件风格并支持键盘操作。开关开启表示保留既有自动拦截，关闭表示该用户不因历史候选超限被直接拒绝。保存和重新打开必须保持状态；取消不改变服务端状态。

#### Scenario: 编辑和重新打开

Acceptance: A1

- WHEN 管理员打开用户编辑并切换开关后保存，再次打开该用户
- THEN 显示已保存状态，中英文均具有清晰标签和说明；取消修改不得产生保存请求。

### Requirement: 默认、持久化与授权

用户策略必须持久化，缺省或旧用户均保留现有行为。管理更新字段可选，省略时不更新，显式布尔值可反复切换。仅管理员用户管理接口可修改，普通用户自助 API 不接受生效。

#### Scenario: 默认与部分更新

Acceptance: A2

- WHEN 创建未指定该字段的用户，读取旧用户，或通过管理员接口省略字段更新其他属性
- THEN 新用户和旧用户默认开启自动拦截；省略字段保留已保存策略，显式启停能够存取；普通用户无法自行修改。

### Requirement: 开启时维持历史超限自动拒绝

全局 Cyber 会话屏蔽开启且用户不属于现有豁免时，现有顺序为先查显式会话键，再检查来源范围是否活跃。来源范围由 API Key、客户端 IP 和归一化 User-Agent 决定。用户开关开启且来源范围活跃时，超过 256 个历史候选直接返回 `transcript_lookup_limit_exceeded`；来源范围不活跃不因历史长度单独拒绝。

#### Scenario: 开启后的边界行为

Acceptance: A3

- WHEN 开关开启，提交 256 和 257 个有效历史项，并分别模拟来源范围活跃与未活跃
- THEN 仅来源范围活跃且超过上限时因溢出拒绝，其余情况沿用正常精确检查或放行。

### Requirement: 关闭时继续有界精确检查

关闭仅取消历史溢出的直接拒绝，不跳过显式会话封禁和当前保留历史候选的查找。历史派生保持现有最多 256 个最近候选，Redis 命令保持既有批量上限与短路行为。不承诺匹配已截断的更早前缀。

#### Scenario: 超限放行和精确命中

Acceptance: A4

- WHEN 用户关闭自动拦截且来源活跃，提交超过 256 个候选的请求
- THEN 无精确命中时不因溢出拒绝；显式会话键或保留的历史候选命中时仍拒绝，查询次数与每次参数规模有界。

### Requirement: 用户隔离和鉴权缓存一致性

该设置覆盖同一用户的全部 API Key，但不影响其他用户。API Key 鉴权数据库投影、用户实体映射、快照序列化和反序列化必须传递策略。保存设置后必须沿用既有用户鉴权缓存失效机制；旧版本缓存不得覆盖新字段。

#### Scenario: 冷加载与热缓存切换

Acceptance: A5

- WHEN 两个用户拥有不同设置，同一用户使用不同 API Key，并在缓存已加载后由管理员切换设置
- THEN 每个 API Key 使用所属用户设置，冷加载和缓存命中一致，保存后缓存重载新策略，旧格式快照按版本失效。

### Requirement: 入口一致性与其他安全行为

现有调用该 Cyber 会话检查的 HTTP 与 WebSocket 入口均必须携带用户策略；模型与平台变化不改变用户开关含义。全局关闭、现有白名单、上游 Cyber 原始错误记录和其他审核保持现有行为；本次不修改生产服务器。

#### Scenario: HTTP 与 WebSocket 使用同一设置

Acceptance: A6

- WHEN 同一用户分别经 HTTP 和 WebSocket 使用现有共享检查入口，或切换到 DeepSeek 等兼容平台
- THEN 均执行其用户级策略，其他安全开关与记录行为不受本开关影响。
